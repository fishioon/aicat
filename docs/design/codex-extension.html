Codex 扩展：开关语义与请求链路

基于提交 aa7c9a3（feat: 新增 Codex 内置扩展）的实现整理。目标一句话：让 Codex 保留自己的 ChatGPT 登录，同时在模型菜单里多出 aicat 已接入供应商的模型。

TL;DR
  • 开关是 aicat.yaml 的 features.codex，缺省关闭；根证书未被信任时不能启用（因为要解密 Codex 到 chatgpt.com 的 HTTPS）。
  • 启用 = aicat 在两个入口上「接管」Codex 的三类请求：模型列表（合并供应商模型）、选了 供应商/模型 的回合（换成供应商密钥转发）、WebSocket 握手（回 426 逼 Codex 走 HTTP/SSE）。其余请求——包括 ChatGPT 自带模型的回合——原样去 chatgpt.com。
  • 停用 = 这一切全部消失：chatgpt.com 的 CONNECT 回到直通，直连入口返回 503，Codex 看到的就是原生 ChatGPT。
  • 开关只影响新连接：切换后需要重启 Codex。

2. 总体架构：两个入口，一个处理器

Codex 可以通过两种方式到达 aicat。两条路最终都落到同一个 internal/codex.Handler，因此行为一致；差别只在「ChatGPT 自带回合」由谁转发。

Codex 发出 aicat 内部 去 ChatGPT（带 Codex 原有登录） 去供应商（只带供应商密钥）

入口 A · 经网关

  • Codex 走系统代理，CONNECT chatgpt.com:443；ShouldIntercept = 名单 || codexAddon.Intercepts 让它被解密。
  • Addon 顺序：api → codex → traffic。codex addon 在 Requestheaders 里调用 Takes()：接管就直接给 f.Response（经 io.Pipe 流式），不接管则交给后面的 traffic addon 按普通请求采集、改写、转发。
  • Responseheaders 给 ChatGPT 原生回复的 X-Models-Etag 也打上 aicat 标记。

入口 B · 直连

  • ~/.codex/config.toml 设置 openai_base_url，Codex 直接打到 aicat 的 HTTP 监听。
  • 不需要系统代理；但根证书仍是开关前提（开关本身统一检查）。
  • 这里没有网关来转发 ChatGPT 回合，所以由 passthrough() 用 ReverseProxy 原样送往 chatgpt.com，并经 traffic.Mirror 记录。

3. 分流决策：一个请求进来后怎么走

「/ 命名空间归 aicat 所有」：带 / 的模型即使不可用也在本机返回 400，绝不回落 ChatGPT——避免把 Codex 的对话误发给 OpenAI，也避免把 ChatGPT 凭据带给错误的上游。

4. 模型列表链路 GET /backend-api/codex/models

ETag 标记：让 Codex 在供应商模型变化时重新拉列表

Codex 缓存列表并记住它的 ETag；每次回合的响应头 X-Models-Etag 与它不同时，Codex 就重新拉列表。aicat 的做法：

  1. tag() = sha256(json(entries(0))) 的前 6 字节 hex——供应商增删、重新同步、models.dev 更新都会改变它。
  2. 列表 ETag 写成 "<后端 ETag>+aicat-<tag>"。
  3. ChatGPT 回合的响应（经网关由 Responseheaders，直连由 passthrough）里的 X-Models-Etag 同样追加标记，于是两者一致，Codex 不会每轮都重拉；一旦供应商侧变了，标记不同，Codex 自动刷新。

5. 供应商回合链路 POST /responses，model = compat/deepseek-v4

直连入口（入口 B）省略前两步：请求直接到 codex.Handler.ServeHTTP，之后完全相同。chatgpt.com 收不到这次请求，供应商也收不到 Codex 的 ChatGPT 凭据。

6. ChatGPT 自带模型回合

经网关

Takes() 返回 false（model 不含 /），body 已放回原字节；请求继续交给 traffic addon，按普通 HTTPS 流量采集与改写后原样发往 chatgpt.com，记录里有改写前后对照与应用归属。响应头上 X-Models-Etag 被追加 aicat 标记。

直连

passthrough()：ReverseProxy 原样转发到 chatgpt.com（登录头保留，去掉 Accept-Encoding 让记录可读），traffic.Mirror 按上游 URL 记录，Authorization/Cookie 记为 [aicat]。

7. 模型从哪来：供应商同步与 models.dev

Anthropic 供应商的模型也会同步，但它不支持 Responses，因此不出现在 Codex 列表里；aicat 不做协议转换。

8. 安全边界

  • 凭据隔离：供应商回合用全新 header 构造，ChatGPT 的 Bearer、Cookie、Account-Id、设备证明都不会发给供应商；供应商密钥只由 provider.Handler 在出站时注入。
  • 不回落：/ 命名空间的模型失败只在本机报 400，不会被送往 chatgpt.com。
  • 记录脱敏：所有 Mirror 记录中的凭据头统一为 [aicat]；e2e 断言密钥不出现在任何记录里。
  • 本机限制：直连入口与 API/MCP 共用监听，只接受本机 peer、拒绝浏览器 Origin。
  • 不污染用户配置：额外解密 chatgpt.com 不写入用户的解密域名名单；停用即恢复直通。
  • 出站直连：codex 与 provider 的 transport 都 Proxy: nil，避免环境代理指回 aicat 自己形成回环。

9. 已知限制

  • 切换开关只影响新连接，已运行的 Codex 需要重启。
  • 供应商模型的对话不支持压缩（/responses/compact 与 compaction_trigger 均 400）；从 ChatGPT 模型中途切到供应商模型时，历史中的加密内容供应商读不了，建议新开对话。
  • 启用期间 Codex 不使用 WebSocket 优化，回落到 HTTP/SSE。
  • 只支持 OpenAI 与兼容 OpenAI 的供应商；模型全部提供，没有勾选。
  • 经网关被接管的请求只有「发往上游」的一条 Mirror 记录，没有改写前后对照和应用归属。
  • 目前只用本机 fixture（e2e/codex.cjs）验证，尚未经真实 Codex / chatgpt.com / 真实供应商验证。
