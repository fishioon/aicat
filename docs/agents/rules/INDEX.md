## 新增规则

先过决策阶梯，在第一个成立的层级停下：

1. 能否改代码结构、类型或 API，让这类错误根本表达不出来？
2. 能否用既有文档（`CONTEXT.md`、`docs/architecture.md`、feature map）澄清，而不是新增约束？
3. 以上都不行，且属于判断力、流程或设计意图 → 才写规则。

只有「不管这次做什么任务都必须知道」的约束才进 `AGENTS.md`，其余一律进 `docs/agents/rules/`。

按下列步骤产出：

1. **命名失败模式**：一句话、行为化、可检索，例如「改了 UI 文案但没同步英文翻译表」。一句话说不清就是两个失败，拆开。
2. **记录证据**：哪次任务、实际做了什么、应该做什么、代价。没有观察到真实失败时不要凭想象造规则；说明缺证据并停下。
3. **判断归属**：一个文件只管一个失败模式，长了就拆。
4. **写规则文件**，使用下面的固定四段；约束写成可观测行为、动词开头；「何时可删」必须是可判定的具体条件。
5. **登记索引**：在上面的表格加一行，填触发条件、来源、状态 `active`、最近命中日期。
6. **收敛 AGENTS.md**：从 `AGENTS.md` 迁出时把原文替换成带触发条件的索引行，不改语义；不追加新段落。

模板：

```markdown
# <主题>

## 何时读
<触发条件：什么任务、什么改动时才需要读>

## 约束
- <可观测行为，动词开头>

## 来源
<日期 + 哪次任务/审查 + 实际发生了什么 + 代价>

## 何时可删
<具体、可判定的条件>
```

迁移的老规则若无留档，「来源」里明确写「原始触发事件未留档」，不要编造。

## 淘汰

失效条件满足、与现状冲突，或「最近命中」长期为空 → 状态改 `deprecated`，下一轮整理时删除文件与索引行，不保留已失效条目。

「最近命中」在改动顺带更新即可，不需要精确统计；长期为空即视为删除候选。
